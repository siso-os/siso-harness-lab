herdr-resurrect

When Shaan powers off or reboots the laptop, this makes his herdr terminal workspace come back to what it was — including the AI agents that were running in each pane, resumed into their prior conversation.

Verified truth (2026-07-02, from herdr-server.log): herdr natively restores the full topology on server start — workspaces (+ custom names), tabs (+ labels), panes (+ cwd) — persisted to ~/.config/herdr/session.json every few seconds. But it spawns those panes as bare shells; it does NOT relaunch the claude/codex agents. Shaan used to re-start each agent by hand after every reboot. That manual step is the only gap this tool fills.

What it does

  1. herdr-snapshot — every 5 min, archives herdr's own session.json (topology + each pane's bound agent_session UUID) to ~/.local/state/herdr-resurrect/, keeping the last 10 + a latest.json pointer. We do NOT re-derive topology — herdr already persists it faithfully; the archive just guards against a bad write and captures the alive-agent binding.
  2. herdr-restore — reads the desired agent bindings (snapshot-first, merged with live session.json), matches each to its now-bare live pane by workspace_id + tab, and runs the resume command into it: 
    claude --resume <uuid> --dangerously-skip-permissions
codex resume <uuid>
    The UUID is the exact Claude/Codex session id, so the same conversation resumes — not a fresh agent.
  3. Two LaunchAgents arm it: an interval snapshotter and a login-triggered restore.

Why snapshot-first (subtle but load-bearing)

When an agent exits cleanly, herdr immediately scrubs its agent_session from session.json. On a real power-off the agents are SIGKILLed, so session.json keeps the binding — but the 5-min snapshot, captured while the agent was alive, is the robust record either way. Restore unions both sources so nothing is missed.

Safety / idempotency

  • Restore only ever injects into a bare shell (a pane where agent and agent_session are both null). A pane that already has an agent is skipped — so a second run, or a run on an already-populated session, is a no-op.
  • It never closes, splits, or creates panes, and never sends input to a pane that already has an agent. Purely additive.
  • The login wrapper waits for the herdr socket, gives herdr time to finish its native layout restore, then guards: if zero desired-agent panes are bare, it skips entirely.

Eyeball readiness (one command)

node ~/.local/bin/herdr-restore --dry-run --verbose

Prints, per persisted agent pane, whether it would RESTORE (bare shell found) or SKIP (agent already alive) — with the exact resume command. On a normal running session every line is SKIP; right after a reboot each would show RESTORE.

Manual controls

# take a snapshot now
herdr-snapshot

# see what restore WOULD do (safe, no changes)
herdr-restore --dry-run

# force a restore now (only touches bare shells)
herdr-restore

# restore purely from the last snapshot (ignore live session.json)
herdr-restore --from-snapshot

# check the LaunchAgents are armed
launchctl list | grep herdr-resurrect

All 11 of Shaan's live panes left untouched. Test workspace cleaned up. PASS.
  • launchd load: both agents loaded; RunAtLoad restore correctly guarded and skipped (0 bare panes) without disturbing any live agent.
  • Remaining unverifiable until a real reboot: that macOS spawns the login restore LaunchAgent after herdr's own session restore has produced bare shells (timing). The wrapper's socket-wait + 8s settle + guard is built for this, and re-running restore is a safe no-op if it fires early.
